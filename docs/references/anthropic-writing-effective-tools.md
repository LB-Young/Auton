## 核心观点

工具不只是开发者 API 的包装，名称、职责边界、返回语义和信息长度都会影响模型使用。文章提倡基于真实任务评测工具。

## 关键机制与做法

- 选择值得实现的工具，命名空间帮助区分能力。
- 返回有意义且节制的上下文，结合执行轨迹改进描述。

## 我的理解

工具应降低决策歧义，但不能替模型包办所有探索。可理解的错误和稳定资源 ID，往往比增加一个“自动修复”接口更有用。

## 对 Auton 的启示

- 工具 envelope 区分业务成功、空结果、权限错误、截断和异步处理中。
- 工具变更绑定 schema 版本，以误用、恢复和任务收益一起验收。

## 局限与适用前提

描述优化不能替代业务校验、身份与幂等；并非越少工具就必然越准。

## 建议验证（尚未执行）

提供相似工具、错误参数和分页结果，检查选择准确、错误可恢复且不误判完成。
