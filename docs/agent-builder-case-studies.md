## 2. C01 · Manus：优化上下文时，缓存、工具历史与错误证据会相互牵制

### 来源报告

Manus 描述了多轮框架重建后的经验：动态改变工具定义会破坏缓存前缀，并使历史中的工具调用失去对应定义；其方案是在稳定定义下控制可用动作。文章还强调可回查的外部文件、目标清单，以及保留失败观测，避免抹去恢复线索。[原文](https://www.manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)

### 暴露出的设计冲突

“减少工具”“减少历史”“减少输出”单独看都合理，但不能只按 token 数优化。删掉工具可能令历史无法解释；删掉错误可能让模型再走同一条路；只留下 URL 又不一定能恢复当时网页。缓存命中和语义完整性是不同目标，必须分别衡量。

### Auton 建议

1. **先保证历史可解释**：每个调用绑定 tool ID 与 schema digest，工具退出可用集合后，仍能读取当时的定义和结果。
2. **区分发现、暴露、授权**：工具发现可按需；暴露策略按 provider 能力实现；授权始终由 Tool Host 执行。不能把“模型选不到”视为“运行时没有权限”。
3. **压缩可回溯**：原始工具结果进入 artifact store，摘要记录 hash、时间、段落定位和读取方式；网页有必要时保存当时内容，不能只靠可变 URL。
4. **保留失败的有效信息**：错误类别、已尝试动作、关键诊断与后续结果保留；冗长重复堆栈可外置。不能把失败原文无限追加作为唯一方案。
5. **测量真实缓存**：稳定序列化和静态前缀；动态时间放到适当位置。缓存实现按 provider 验证，不假设所有接口支持相同的 mask、prefill 或缓存语义。

### 待做实验

固定任务和模型，对比“动态删除工具”“稳定定义+受控可用集合”“按需发现+保留版本化历史”。检查工具误用、历史一致性、缓存命中、费用和最终成功率。再比较错误完全隐藏、错误摘要、完整错误三种恢复策略。

**不能推出**：工具必须永远全部常驻；原始错误必须始终留在活动上下文；某个 provider 的解码技巧可以直接成为 Auton 跨模型接口。

## 3. C02 · Vercel d0：过度专用工具可能让模型与团队同时被框架束缚

### 来源报告

内部 text-to-SQL Agent d0 原先有大量 schema、查询计划和恢复工具，维护脆弱。团队改为让模型在沙箱中直接读取结构良好的语义层文件，再执行 SQL。公开比较仅有 5 个代表查询，成功数从 4 个变为 5 个；作者强调其文件本身已有清楚定义。[原文](https://vercel.com/blog/we-removed-80-percent-of-our-agents-tools)

### 关键前提

案例中的数据语义层不是随意堆放的原始数据。删除检索包装后，模型仍然获得了有组织的业务知识；也没有因此消除执行 SQL 的真实业务边界。它比较的是两套具体实现，不是证明 bash 普遍胜过所有类型化工具。

### Auton 建议

- 将工具分成三类：**检索与导航辅助、业务动作、权限与一致性控制**。第一类可尝试简化；后两类不能因“模型更聪明”全部删除。
- 文档、命名、接口与文件结构应作为一等能力建设。Skill 不应反复替代本可以写清楚的项目事实。
- 对每个新增专用工具记录：解决哪个已观察失败、减少哪些步骤、引入多少 schema 与维护负担、何时可以退役。
- 简化方案进入对照实验时，保留同一数据权限、模型预算和验收标准，防止用更宽权限换出表面收益。

### 待做实验

准备三组任务：代码导航、语义层查询、外部写操作。分别比较专用工具、文件+bash、混合工具。除成功率还记录维护改动量、任务回合、越界尝试与首次定位时间。样本要覆盖未见 schema 和业务例外。

**不能推出**：5/5 是长期 100% 可靠；任意文件目录都能替代语义建模；业务写操作也应该只暴露自由 shell。

## 4. C03 · Braintrust × Vercel：评测显示“工具差”，可能同时是环境与答案错

### 来源报告

团队比较 SQL、bash 与基础文件工具，初始结果明显偏向 SQL。调试发现文件访问性能问题、缺少 schema、参考答案错误或歧义及加载缺陷。修复后差距缩小，混合方案通过文件探索复核 SQL，可靠性更好但成本更高。[原文](https://vercel.com/blog/testing-if-bash-is-all-you-need)

### 为什么特别值得参考

这是对 C02 的有用补充：不是从一个“更强抽象”直接跳到另一个，而是追踪错误发生在哪一层。工具代码、输入说明、数据加载和评分器都可能改变结论；修正评分器也必须有独立理由，不能为了保护喜欢的方案而改答案。

### Auton 建议

1. 失败至少分为模型选择、工具能力、工具实现、环境、数据和 checker 六层，允许多因共同作用。
2. 每个评测数据集具有 manifest：数据 hash、行数、加载方式、schema、基准答案版本和已知歧义。
3. 判断“多余验证是否浪费”要看它是否降低错误，而不是单看工具调用数。高价值任务可允许更贵的交叉核对。
4. checker 修正进入单独审查，记录旧答案、错误证据和新版；在固定新版本上重新评所有候选，不只重跑受益方案。
5. 性能工具基准与 Agent 任务基准分开；先证明读取一批文件的接口满足必要时限，再比较模型策略。

### 待做实验

向一个已知正确数据集注入：遗漏一行、重复一行、错误 golden answer、模糊分组定义、文件扫描缓慢。要求报告正确指出根因，不自动修改 Agent 提示“修复”这些问题。

**不能推出**：SQL 永远更准或混合工具必然更好；原始一轮分数可以代表修复后的性能；增加验证总值得成本。

## 5. C04 · Parcha / Grep：一个成功执行的条件分支，批量遗漏了应有搜索

### 来源报告

AJ Asver 复盘：负面新闻流程原本应查询 Google News 后再做更广搜索，代码却仅在前者无结果时做后者。少量无关结果会阻止补查，作业正常结束却漏信息。团队暂停、修复并重跑受影响工作，随后加强关键路径监控与追踪。文章也回顾了自由循环、固定流程与可配置架构的反复取舍。[原文](https://operatorsguidetoai.substack.com/p/ten-lessons-learned-from-three-years)

### 这不是“工作流或自主 Agent 二选一”

事故证明一条具体分支写错，以及原监控不足以发现它；不能证明让模型自由判断就一定不漏查。确定性代码和模型都需要接受完整性验证。关键是把“搜索得到了结果”与“搜索已覆盖要求”分开。

### Auton 建议

- 建立 **Coverage Ledger**：每项必需检索范围、实际执行来源、证据质量、不足项与跳过理由。`has_results` 不直接等于 `sufficient_evidence`。
- 给可选路径与必需路径不同控制语义：必需路径若跳过，必须有可审查的规则或用户授权；模型推荐跳过不能直接改完成条件。
- 关键确定性分支做对抗 fixture：首路为空、无关但非空、仅一条、相互矛盾、已过期、有害注入。关注语义而非仅分支覆盖率。
- 生产结果可按规则版本和执行分支查询影响面。事故发生后能定位“哪些任务跳过了更广搜索”，而不必用模型扫全部报告猜测。
- 保留受控探索入口：固定流程明确不足时，进入“补充调查”状态，原必需项仍需履行。

### 待做实验

设计一个双来源搜索任务：第一路始终返回无关的非空结果，第二路有关键证据。比较现有流程、显式覆盖规则、模型充分性判断和组合方案；同时记录漏查率、误扩展率、费用与重跑定位成本。

**不能推出**：固定流程普遍不可靠；文章自报事故规模和商业结果经过独立审计；增加日志即可防止逻辑错误。

## 6. C05 · Managed Agents：会话、推理循环和沙箱同生共死，恢复与调试都困难

### 来源报告

Anthropic 将 session、harness、sandbox 放在同一容器时，容器故障会连带会话，流式事件难以区分故障来源，容器中的用户数据又限制人工调试。后来拆成独立接口，并将凭据移出生成代码可访问的沙箱；持久会话还支持回查历史。[原文](https://www.anthropic.com/research/managed-agents)

### 对 Auton 的具体意义

即便首期只跑一个本地进程，也应先划清接口与数据生命周期，不一定立即部署三个服务。持久会话不应靠沙箱目录“刚好还在”；恢复控制循环与恢复工具工作区是两个步骤。

### Auton 建议

1. **Session Store**：保存目标、事件、checkpoint、未决操作引用；不依赖一次 worker 或 sandbox 的生存。
2. **Harness**：只持有可重建控制状态；崩溃后依靠版本化结果恢复，不以重新请求模型代替状态恢复。
3. **Workspace/Sandbox**：有 provision recipe、资源 manifest、产物检查点和销毁规则；重建后不能假设未提交文件仍存在。
4. **Credential Broker**：受控代理注入访问能力，模型生成代码拿不到通用长效凭据；代理仍检查资源和动作权限。
5. **调试边界**：运维看元数据与脱敏证据；需要读取敏感 payload 时单独控制，不能默认允许工程师进入用户环境。

### 待做实验

分别杀掉 UI 流、harness、sandbox，要求三种故障可区分。恢复后检查目标仍在、产物可定位、在途副作用进入对账；再让生成脚本尝试读凭据，确认秘密未进入其权限范围。

**不能推出**：把容器换成服务即可实现 exactly-once；持久事件自动保存所有工作区内容；新容器重试所有工具调用一定安全。

## 7. C06 · 长应用构建：实现者自评过于乐观，压缩也不能解决全部长任务问题

### 来源报告

文章描述长任务上下文失去连贯性、部分模型提前收尾，以及自评偏宽松。实验采用结构化交接与上下文重置，并分离 planner、generator、evaluator；作者说明独立 evaluator 仍需校准。文中应用评审还区分了外观完成与真实交互深度。[原文](https://www.anthropic.com/research/harness-design-long-running-apps)

### Auton 建议

- 将验收分为静态存在、可运行、主路径可交互、边界条件、用户体验等维度。截图好看不能替代交互检查。
- 独立 evaluator 只获得执行验收所需规格、产物与环境入口，先独立判断；发现缺陷给可复现路径和证据，不仅给低分。
- 对 generator-evaluator 循环设置总预算、重复意见合并、阻塞缺陷标准和最终裁决；不允许审查者不断扩充用户原范围。
- reset 与 compaction 作为可选择策略，记录触发原因、交接内容和丢失风险。模型升级时重新验证，别把旧模型补丁固化成永远正确。
- 任务状态需要可机读，不只写一份“下次继续”的 Markdown；交接保留未知操作、授权、版本与未通过验收。

### 待做实验

用看似完整但按钮无功能的应用、只覆盖 happy path 的实现和真实完整实现做盲评；再比较无压缩、摘要和重置+结构化交接的长任务收益。记录 evaluator 的误报/漏报及每次有效修复成本。

**不能推出**：只要加一个 critic 就能保证质量；重置对所有模型有效；主观评分能完全代替用户判断。

## 8. C07 · 编译器 Agent 团队：共同瓶颈无法靠增加 worker 解决

### 来源报告

并行编译器研究中，独立失败用例容易分工；进入 Linux 内核构建后，多个 Agent 都遇到同一 bug 并覆盖修改。作者用 GCC 混合编译作为对照，把大失败分解到文件子集，还需定位文件组合故障。测试反馈过长、跑测试耗时和新增功能破坏旧功能也需要专门处理。[原文](https://www.anthropic.com/research/building-c-compiler)

### 本例对多 Agent 的核心启示

“增加分工提示”不一定能解决问题，因为当时缺的可能是可独立验证的子问题。任务只有一个全局失败信号时，任何 worker 都会追同一个表面症状；需要先改善诊断粒度，再扩大并发。

### Auton 建议

1. planner 判断委派前提：能否分出互不覆盖的变更范围？每个子任务是否有可独立观测结果？
2. 对共享瓶颈，先派一个诊断任务做失败缩减、差分或二分定位，不同时派多个 worker 做同一修复。
3. 独立子问题出现后，建立任务 owner 与输入版本；整合阶段验证组合效果，单项通过不保证组合通过。
4. 测试分 fast subset 与完整集，前者辅助探索，后者负责发布；抽样种子与覆盖范围写入报告。
5. 输出短摘要与可搜索错误文件，记录实际测试耗时。预算管理器控制时间，不能要求模型凭感觉决定测试是否跑太久。
6. 使用 oracle 的测试明确哪些行为依赖 oracle；不能把辅助基准偷偷算成自己实现的能力。

### 待做实验

构造三个小项目：独立缺陷集、单一共享阻塞、两个组件单独正常但组合失败。分别用 1/2/4 worker，测量交付成功、重复修改、诊断耗时与总成本；验证“先缩减再委派”是否优于直接扩容。

**不能推出**：研究原型的锁文件协议可以直接用于生产；无限执行循环适合个人电脑；构建某个大项目成功等于实现已具备完整兼容性。

## 9. C08 · Uber Finch：路由准确与子 Agent 准确必须分开测

### 来源报告

Finch 采用 supervisor 与数据/文档子 Agent。文章明确讨论相似工具与含糊问题导致的意图碰撞，分别评测子 Agent、supervisor 路由及端到端表现；SQL 以查询结果对照而非字面 SQL 相同判定。按需人工验证在文中属于后续规划。[原文](https://www.uber.com/us/en/blog/unlocking-financial-insights-with-finch/)

### Auton 建议

- 将“选错专家/数据源”和“专家选对但执行错”分开归因，避免围绕错误层反复改 prompt。
- 为每个 role 维护能力说明：数据范围、输入条件、工具、返回结构、需要澄清的边界。不同 role 不能只有名称不同。
- 路由置信度低且数据源差异会影响结果时，做低成本探测或请求澄清；不能把一个不适用的专家返回空结果当作真实不存在。
- 数据任务验证结果语义、时间范围、单位与过滤条件，不要求与 golden SQL 逐字相同。
- 人工复核是独立状态：requested、reviewing、verified/corrected；尚未复核的结果不能展示为已人工确认。

### 待做实验

准备相似任务分别需要项目文件、运行数据库或产品文档；加入名称相似、同一词不同业务含义和不应使用任何工具的例子。分别测路由、专家、聚合与端到端，显示错误转移矩阵。

**不能推出**：增加专家数量会自动提高覆盖；文章规划功能已经上线；财务结果可以仅靠 LLM Judge 验证。

## 10. C09 · Cloudflare Code Mode：减少模型搬运，不等于减少运行时责任

### 来源报告

Cloudflare 将 MCP 工具转换为 TypeScript API，让模型生成代码组合调用，减少中间结果反复经过模型。代码在隔离运行时执行，通过受控 bindings 访问 MCP，文中实现限制普通出网；这是执行架构，不是给模型自由 eval 的建议。[原文](https://blog.cloudflare.com/code-mode/)

### Auton 建议

- 对确定性映射、过滤、聚合和批量读取，允许代码在数据附近执行，最后只返回必要摘要与产物引用。
- 控制粒度不能只剩“一次脚本”：内部每个外部写仍要经过身份、批准、operation ledger 和预算；脚本超时后逐项核实。
- 代码不能直接拿通用网络或凭据绕过工具代理；受控 API 类型说明不是权限检查。
- 大批量任务区分只读与写入。只读可更积极自动批处理；有写入则逐项记录结果并明确部分失败语义。
- 代码返回值、stdout 和异常分别记录；异常前可能已有副作用，不能因脚本失败整体重跑。

### 待做实验

比较逐工具调用和代码组合的多步读取，测 token、延迟和准确性；再注入第 N 次写后脚本崩溃，检查逐项账本和恢复。尝试脚本直接出站，确认边界仍在。

**不能推出**：少了模型调用就一定更安全；JavaScript isolate、容器和本地子进程提供相同隔离；写一个代理就能保证外部业务幂等。

## 11. C10 · Project Vend：更好的工具与多 Agent 约束有帮助，但不能消除讨好和越界

### 第一阶段来源报告

Claudius 在店铺实验中出现过错误收款信息、亏本报价、轻易提供折扣等问题，而且口头承认错误后也未必稳定改正。实验包含人类执行现实操作，不能当作完全无人系统。[第一阶段](https://www.anthropic.com/research/project-vend-1)

### 第二阶段来源报告

后续同时升级模型、说明与工具，增加 CRM、成本可见性及 CEO Agent。业务表现改善，但仍有受对抗性交互影响的问题；作者明确阶段并非严格分隔。采购付款仍保留人工边界，因此不能把改善单独归因于 CEO。[第二阶段](https://www.anthropic.com/research/project-vend-2)

### 对 Auton 的具体意义

个人 Agent 也会面对不同诉求：当前对话中的请求者、资源 owner、长期目标、操作授权可能不是同一方。多一个“老板 Agent”不会自动建立可信身份，也不保证两个模型不会一起接受错误前提。

### Auton 建议

1. 资源地址、收件人、付款账号等从受控配置读取和核实，不由模型临时猜测。
2. 区分“用户反馈”“外部参与者要求”“高权限批准”；不能通过语气、职位称呼或自称熟人获得能力。
3. 重要数字在动作时可见：预算、成本、报价、数量、约束；不能只在历史里提过一次。
4. 关键门禁由代码执行。策略允许破例时，批准绑定具体动作和期限；另一个 Agent 的自然语言同意不是用户授权。
5. 评测包含长周期反馈和对抗性交互，而不只测友好输入下的单次成功。

### 待做实验

用不涉及真实支付的模拟业务：角色伪装、请求例外、长期重复说服、错误资源地址、成本变化。比较单 Agent、双 Agent 审核、确定性门禁与混合方案，记录违规而不只看平均收益。

**不能推出**：财务改善证明多 Agent 优于单 Agent；会认错就形成长期学习；一个友好内部环境足以代表开放部署。

## 12. C11 · Claude Code 质量复盘：模型不变，配置和上下文仍可能造成退化

### 来源报告

Anthropic 将一轮质量报告追溯到三项不同变更：默认 reasoning effort 调整；本应一次执行的历史清理错误地持续每轮发生；减少冗长的提示变更与其他修改组合后损害编码质量。影响流量和时间不同，整体上显得不一致；作者报告已回退或修复。[原文](https://www.anthropic.com/research/april-23-postmortem)

### 为什么值得作为发布设计输入

诊断只记录模型名称会漏掉真正变量。“输入更少、响应更快、缓存更好”是资源指标，不代表复杂任务质量保持。多个小变化叠加后，还可能只伤害特定长度、空闲恢复或任务类型。

### Auton 建议

- RunManifest 至少包含 runtime build、prompt bundle、effort、截断/压缩策略、缓存策略、工具 schema、Genome 和实验 cohort。
- 变更按机制分开发布与回退，避免同时改模型、提示和上下文然后无法归因；必须组合发布时记录组合版本。
- 评测覆盖长会话、空闲后继续、多个复杂度层级和真正用户任务；聚合平均分之外按 cohort 分层。
- 状态性优化测试“第一次、第二次、第 N 次”，不只测优化触发的那一轮；明确状态标志何时清除。
- 质量下降时先核对 runtime 与策略差异，再决定是否修改记忆或 Skill；不能让 Evolution Engine 掩盖运行时缺陷。

### 待做实验

构造一次性历史清理标志，模拟空闲恢复后连续多轮；逐轮比较可见上下文和完成质量。再做 effort × 会话长度 × 任务复杂度矩阵，检查性能改善是否以某类任务退化为代价。

**不能推出**：所有质量投诉都来自 harness；高 effort 总是最优；作者自报修复等于我们已验证全部影响消失。

## 14. 建议新增的 12 个实验

编号使用 X 前缀，避免与原手册 F01–F64 混淆。这些是待实现方案，不代表本轮已运行。

| ID | 设计问题 | 对照与注入 | 观察与判定 |
|---|---|---|---|
| X01 | 动态工具集是否值得 | 相同任务对比稳定/动态/按需发现，固定权限 | 正确率、schema 误用、缓存、费用；不只看 token |
| X02 | 哪种错误保留最利于恢复 | 隐藏、摘要、全文三组，重复可恢复故障 | 再犯次数、恢复率、上下文膨胀 |
| X03 | 是否过度构建专用工具 | 专用工具、文件+bash、混合三组 | 未见任务、维护成本、权限行为与质量 |
| X04 | 工具差还是评测差 | 错答案、漏行、慢 IO、缺 schema 单独注入 | 根因分类、修复后全候选重测 |
| X05 | 有结果是否意味着覆盖充分 | 第一路无关但非空，第二路含关键证据 | 漏查率、补查成本、覆盖日志 |
| X06 | 控制循环是否独立于沙箱 | 分别中断 stream、harness、sandbox | 可区分、可恢复、未知副作用可对账 |
| X07 | 自评与独立验收差多少 | 静态好看/交互残缺/真实完整三类产物 | 误报、漏报、缺陷可复现、修复成本 |
| X08 | 多 Agent 是否真能扩展 | 独立缺陷/共享瓶颈/组合缺陷，1/2/4 worker | 总成本、重复修改、整合成功、有效吞吐 |
| X09 | supervisor 路由是否正确 | 相似词不同数据源、空结果、无适用专家 | 路由与专家准确率分别报告 |
| X10 | 代码模式的副作用是否可控 | 多步脚本第 N 次写后崩溃/取消 | 无盲重试，逐项 operation 与真实外部状态一致 |
| X11 | 多 Agent 审核能否抵抗说服 | 模拟例外请求、角色伪装、重复说服 | 与代码门禁对比，任何越权单独计数 |
| X12 | 运行时优化是否退化质量 | 一次性历史清理、effort、会话长度组合 | 第一次/第 N 次状态、cohort 质量、回退可用 |

实验先从离线小 fixture 开始，安全与一致性检查尽可能不依赖模型；涉及质量时再用实际模型重复运行。将预算、环境、任务集与随机因素写入实验报告，避免从单次成功推断普遍有效。

## 15. 哪些结论现在可以采纳，哪些还不能

### 可以直接进入接口与边界设计

- 保留稳定、可追溯的输入/配置/产物版本；会话不等于活动上下文。
- 模型生成代码与长效凭据分离；所有工具路径经过同一控制层。
- 多 Agent 委派必须有可验收子问题、明确 owner 与集成责任。
- 固定流程也要验证业务完整性；成功退出不是成功完成。
- 优化配置、提示、上下文和依赖也要版本化，不能只记录模型 ID。

这些是本轮提出的保守设计选择，仍需通过对应契约测试和部署环境验证。

### 必须实验后才能成为默认策略

- bash 是否优于专用检索，是否应使用 SQL/文件混合。
- reset、compaction、fork 各自适合哪些模型与任务。
- evaluator 值不值得额外预算，多少轮后应停止。
- 何种并发量、分工方式和诊断粒度能提高真实交付吞吐。
- 缓存命中、费用、延迟和质量之间的可接受取舍。

### 目前仍缺的证据

本轮加强了公开一线案例，但没有审计这些团队的私有实现、独立核实其全部商业结果，或复现其完整实验。对 Auton 来说，长期真实任务分布、工具适配器的幂等能力、模型迁移后的收益保持，仍要靠自有实验补足。公开资料中的成功方案也可能保留未披露失败。

建议下一步围绕 X05、X06、X08、X12 做小规模验证：它们分别检验业务覆盖、故障恢复、多 Agent 价值和运行时变更风险，能直接影响架构骨架。本文作为设计资料，不自动改写架构正文中的既定决策。
